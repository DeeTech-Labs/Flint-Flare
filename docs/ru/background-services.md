# Фоновые services во Flare

Diagnostics показывает установленные service components и подтверждённые Core состояние, причину, поколение экземпляра, использование памяти и ограниченные счётчики выполнения. Метаданные опрашиваются каждые 500 мс, пока страница и окно активны. Протокол не передаёт состояние приложения, IPC-сообщения или отсчёты датчиков.

Счётчик callbacks означает пачки dispatch: один runtime tick может доставить несколько Lua events/timers с общим бюджетом. Максимальное время callback относится ко всей пачке. Счётчик dispatch не измеряет физические пробуждения ОС.

Запуск, остановка, пауза, возобновление и отзыв выполнения выполняются явно. Запуск не выдаёт `app.background.execute`. Кнопки разрешений запрашивают согласие через стандартный пакетный permission API. Для автозапуска отдельно нужны разрешение `app.background.autostart` и включённая политика автозапуска service. Отзыв разрешения выполнения останавливает service; сама декларация доступа его не предоставляет. Разрешения датчиков и остальные разрешения приложения доступны в Ignite Hub.

Закрытие панели и disconnect Flare прекращают мониторинг и не отправляют команду остановки service. Владельцем services устройства остаётся Core. Приостановленные из-за низкого запаса энергии services могут возобновляться после отмены этой политики Core; ручная пауза требует явного возобновления. Фактические ограничения и ошибки устройства являются источником истины.

## Simulator

Локальный simulator использует тот же Core SDK. Его явная виртуальная политика допускает два service slots, лимит резервирования фона 128 КиБ и виртуальный бюджет доступности для admission 512 КиБ. Это настройки simulator, а не измерения и не гарантии RAM устройства. Учёт wall time использует реальные монотонные часы. Переключатель **Симулировать низкий запас энергии** меняет только политику simulator и не изображает физическую батарею.

Пример SDK `examples/thermometer-service/project.json` содержит независимые foreground `main` и background `worker`, отдельные Lua sections и общие source includes. Установите собранный пакет, явно разрешите выполнение и датчики температуры/влажности, затем откройте UI приложения для просмотра shared state. Метаданные service эти значения не экспортируют. Декларация примера не включает автозапуск. Disconnect simulator уничтожает локальный экземпляр симулируемого устройства; это не проверка сохранности при физическом отключении кабеля.

## Сборка и проверки

Интеграция требует development contract SDK `0x20261114` и пересобранные пакеты FLM3 с явными budget, capabilities, permissions и logic каждого component. Старые root-поля отклоняются. Во Flare закреплён проверенный SDK commit `845590f30df617f035a335b3beb6a12ba51e15ee` в `platform/`. Инициализируйте submodule и используйте обычную конфигурацию по умолчанию:

```powershell
git submodule update --init --recursive
cmake -S . -B build/background-services
cmake --build build/background-services --config Debug
ctest --test-dir build/background-services --output-on-failure -C Debug
```

Используйте обычное окружение Qt/compiler; relocated SDK tests также требуют нужные generator/compiler в окружении. `background_service_sessions` проверяет установку реального пакета, явные разрешения, независимость foreground/service, прекращение скрытого мониторинга, energy/manual pause, флаги автозапуска и отзыв выполнения через Core. Физический admission ресурсов, battery policy, USB/BLE disconnect, reboot/прерывание питания и визуальная компоновка требуют отдельных аппаратных/ручных проверок. Выигрыши задержек, энергопотребления и RAM не заявляются.

Если существующий CMake cache указывает на соседний SDK, перед проверкой consumer с закреплённой ревизией укажите `-DFLINT_PLATFORM_DIR=<Flare checkout>/platform`.
